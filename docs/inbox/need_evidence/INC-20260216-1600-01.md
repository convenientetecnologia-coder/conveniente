## Sintoma (relato humano)

- Após reiniciar o RM3 e executar "Abrir Todos", o sistema inicia saudável (`120/120 ativos`, `118 trabalhando`) com cerca de `~11GB` livres.
- Em 3-6 horas, a RAM livre cai para perto de `~2GB` mesmo com parque de contas parecido.
- A partir desse ponto, o sistema entra em ações defensivas (fechar navegador/parar trabalho), que o operador percebe como modo destrutivo.

---

## Pergunta central do INC

Por que a RAM livre degrada ao longo das horas (mesmo sem aumento proporcional de contas abertas) e quais componentes retêm memória no ciclo real de produção?

---

## Hipóteses iniciais (sem concluir causa raiz)

1. **Acúmulo em abas Messenger (renderer/DOM/cache JS)** ao longo do atendimento contínuo.
2. **Crescimento de contexto em páginas com alta atividade** (conversas, eventos, observers, timers) sem reciclagem suficiente.
3. **Política de recuperação tardia**: o sistema reage quando a RAM já está baixa, em vez de manter headroom estável.
4. **Contribuição secundária do Robe** (picos de postagem) somada ao baseline elevado do Virtus.
5. **Medição com baixa granularidade causal** (sabemos RAM total/livre, mas não "quem" está consumindo por aba/processo no tempo).

## Correção cirúrgica aplicada — fase 1 (overhead monitor/loop)

Arquivo alterado:
- `C:\conveniente\scripts\worker.js`

Problema técnico identificado:
- no caminho normal (`forceRefresh=false`), quando cache de PIDs expirava, o código podia disparar tracing novamente durante o loop de atualização de todos os controllers;
- isso quebrava o orçamento de refresh por tick e elevava `tickMs`/pressão de Node em carga alta.

Correções aplicadas:
1. **Tracing pesado restrito ao orçamento forçado**
   - `getControllerPidsCached(..., forceRefresh=false)` não dispara mais tracing;
   - passa a usar cache existente (inclusive expirado) e fallback leve por `rootPid`.
2. **Cache TTL ampliado**
   - `RAM_PIDS_CACHE_TTL_MS`: default `90s -> 180s`.
3. **Tick de monitor no Windows suavizado**
   - `WIN_RAM_TICK_MS`: default `12s -> 15s`.
4. **Diagnóstico adicional**
   - novo contador `staleHits` em `ramDiagCounters` para medir uso de cache expirado (stale) com segurança.

Validação local:
- `node --check scripts/worker.js` => OK
- lint `scripts/worker.js` => sem erros
