## Contexto

Provision e delete só são “atômicos” se o **canal de comandos** e o **ACK** forem confiáveis:

- comando entregue 1x (ou reentrega idempotente)
- ACK nunca “some” (retry persistente)
- `commands.json` nunca pode degradar silenciosamente (read/parse/write/lock)

Sem isso, existe risco P0 de:

- perfil criado no host sem CT registrar (duplicação posterior)
- comandos presos em `inflight`
- GC/limpeza soltar reservas no CT enquanto o host já mudou estado

## Critério de “done”

- `commands.json` não possui fallback silencioso destrutivo: qualquer corrupção/IO vira estado explícito e recuperável
- `writeCmdQueue(...)` é verificado em pontos críticos (sem “ACK aplicado mas não persistido”)
- ACK do host é persistente + retry-safe (reboot não perde ACKs pendentes)
- Requeue/replay do mesmo `cmdId` é idempotente (não reexecuta `stock_provision` nem `delete_perfis`)
- Existe telemetria suficiente para provar “entregou? executou? ACK chegou? CT aplicou?”
