## Hipóteses (a provar) — com referência de código

### H0) “Fallback para []” ao ler `perfis.json` durante `stock_provision` (gera wipe para 1 perfil)

Como o `stock_provision` cria perfil via `POST /api/perfis`, o fluxo de escrita é:

- `C:\conveniente\scripts\api_perfis.js` (rota `POST /api/perfis`) chama `fileStore.withPerfisFileLockUpdate()`
- `C:\conveniente\scripts\fileStore.js` (`withPerfisFileLockUpdate`) faz `readJsonSafe(perfisPath, [])`
- `readJsonSafe()` **retorna fallback** (`[]`) quando o arquivo está ausente **ou** com JSON inválido
- o mutator faz `next.push(perfilObj)` e grava o array resultante

Resultado: se `perfis.json` estava ilegível/ausente naquele instante, o sistema grava um `perfis.json` contendo **apenas 1 perfil** (o recém criado) — exatamente o sintoma observado (103→1).

O que falta para “provar”:

- evidência de erro de leitura/parse/ausência do arquivo no host no momento do comando (stdout/stderr/issues_fallback/provision_audit),
- e/ou evidência de concorrência/crash na janela (processo duplicado, reboot, IO).

### Nota: “Fechar todos” (close-all) não grava `perfis.json` (mas grava `desired.json`)

Fato (código): `POST /api/perfis/close-all` faz:

- lê `perfis.json` para listar targets (`fileStore.loadPerfisJson()`),
- grava `desired.json` via `fileStore.withDesiredFileLockUpdate(...)`,
- chama o worker para `deactivate` sequencial.

Ou seja: **Ctrl+C durante close-all** é uma suspeita válida de crash/IO, mas o “write” direto do close-all é em **`desired.json`**, não em `perfis.json`.

### H1) Arquivo some por janela de IO (unlink→rename) + crash (sem comando CT)

Fato técnico: `writeJsonAtomic()` apaga o arquivo original antes de renomear o tmp.

- Código: `C:\conveniente\scripts\fileStore.js` (`writeJsonAtomic`)

Risco: se o processo morrer **entre** `unlinkSync(file)` e `renameSync(tmp,file)`, o arquivo pode ficar **ausente**.

### H2) Arquivo ausente foi recriado vazio (bootstrap) e o sistema “começou do zero”

Fato técnico: existe `ensurePerfisJson()` que cria `perfis.json` com `[]` se não existir.

- Código: `C:\conveniente\scripts\fileStore.js` (`ensurePerfisJson`)

### H3) Sobrescrita por shard / subconjunto do cluster

Fato técnico: o `worker.js` tem `loadPerfisJson()` que filtra por shard e há proteção explícita para impedir write de shard no arquivo global.

- Código: `C:\conveniente\scripts\worker.js` (`loadPerfisJson` filtrado por shard; `savePerfisJson` bloqueia write em shard e registra `perfis_write_blocked_worker_shard` em `provision_audit`)

Aqui a pergunta forense é binária:

- existe evidência de `perfis_write_blocked_worker_shard` perto da janela do wipe?
- existe algum outro caminho que gravou perfis “parcial” sem passar por esse bloqueio?

### H4) Comando destrutivo (migrate/cleanup/delete) reescreveu JSON indevidamente

Evidência precisa vir do CT:

- `commands.log` (enqueue/deliver/ack)
- `ack_<cmdId>.json` de `delete_perfis` / `profiles_cleanup` / `migrate_profiles` no intervalo
