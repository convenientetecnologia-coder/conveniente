## Sintoma (humano)

- No RM5, com apenas 1 navegador aberto para teste, ao clicar **“liberar Robe pra postagem”** ocorre erro dizendo que **“não tem foto para aquela conta”**.
- Isso não faz sentido porque existe um pool grande de fotos (~1700) no servidor.
- Regra esperada: o sistema **não deve repetir foto por conta**; há um **registro** de fotos já usadas por conta. Se uma foto for apagada, o registro também deveria ser limpo.

## Como deveria ser (alvo)

- Ao liberar postagem, o Robe deve selecionar uma foto válida do pool, respeitando “não repetir por conta”.
- Se o registro de “já usada” apontar para foto inexistente, o sistema deve se auto-corrigir (limpar/ignorar aquela entrada) e continuar, sem “esgotar” falsamente.

## Critério de sucesso (validação objetiva)

- Ação “liberar Robe pra postagem” **não** falha com “sem foto”.
- Logs provam:
  - pool detectado (contagem > 0),
  - seleção de foto (path/ID),
  - registry por conta atualizado de forma consistente,
  - e, se houver foto inexistente, auto-heal (remoção do registro inválido) com evento audível.

## Evidência por código (já encontrada)

- **Onde o “sem foto” nasce**:
  - `C:\conveniente\scripts\robe.js` chama `fotos.pickPhotoForAccount(nome, workingNames)` e, se receber `{ ok:false, error:'no-photo-available' }`, o fluxo lança `Error("Sem foto disponível...")`.
- **Como uma conta pode “esgotar” foto sem ter postado tudo**:
  - Antes do patch deste INC, `C:\conveniente\scripts\fotos.js` marcava `postedBy` já no momento da **reserva**.
  - Além disso, o `robe.js` continha um caminho “fail-closed” que marcava a foto como usada mesmo quando a postagem falhava.
  - Em cenário de erro técnico/retentativas, isso pode consumir o pool “no papel” e levar ao estado `no-photo-available` mesmo com fotos existentes no disco.

---

## Patch aplicado (mudança mínima, com logs)

Objetivo: evitar travar operação por inconsistência do registry e evitar “esgotar” foto por conta por falhas técnicas.

- **Alteração A — `fotos.js`**:
  - `pickPhotoForAccount` agora **apenas reserva** (`reservedBy`) e **não** marca `postedBy`.
  - Novo auto-heal: `clearAccountHistory(nomeConta)` remove `postedBy` e `reservedBy` daquela conta no índice (somente para destravar conta “sem foto”).
- **Alteração B — `robe.js`**:
  - Se `pickPhotoForAccount` retornar `no-photo-available`, executa **1x** `clearAccountHistory()` e tenta o pick novamente.
  - Em falha/abort sem publicação confirmada, chama `releaseReservation()` para não deixar reserva presa bloqueando o pool.
  - O commit de `postedBy` segue apenas no caminho de sucesso (publicação confirmada via `markPostedAndMaybeDelete`).

Rollback:
- `git revert` do commit do patch + restart do node no host afetado.

---

## Hipóteses (a validar com evidência)

- **H1 — Registry corrompido / key errada**: o registry de “fotos usadas” está indexando por chave errada (ex.: cidade/servidor ao invés de profile), ou mistura perfis, levando a “esgotou” sem esgotar.
- **H2 — Limpeza removeu foto, mas não limpou registry**: arquivo some do disco, mas o registry continua, e o algoritmo trata “missing” como “já usado” + não tenta outra, resultando em erro.
- **H3 — Pool path errado**: o RM5 tem fotos, mas o código está lendo outra pasta (env/config/relativo) e encontra 0.
- **H4 — Concorrência/lock**: outra rotina “deleta/rotaciona” fotos enquanto a postagem está tentando ler, e não há retry-safe.
