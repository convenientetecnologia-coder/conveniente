## Respostas às dúvidas do humano (com evidência de código)

### A) O envio `/report` pode atrasar/falhar por concorrência/carga no host?

**Sim, pode.** O envio do `/report` é executado pelo próprio processo Node do `conveniente` (monitor `dashboard.js`), então depende:

- do **event loop** (se houver bloqueio/lag, timers atrasam),
- do **tempo de coleta do status** (inclui chamada HTTP local para `/api/status`),
- do **tempo de rede/endpoint** (POST para o CT),
- e de uma trava de **anti-overlap** (`inFlight`) que faz o tick “pular” se o anterior ainda não terminou.

Evidências:

- `C:\conveniente\scripts\dashboard.js`
  - `startDashboardMonitor()` roda `tick()` e faz `setInterval(..., INTERVAL_MS)` (`INTERVAL_MS` vem de `DASHBOARD_INTERVAL_MS`, default 30000ms).
  - `tick()` tem `if (inFlight) return;` e `inFlight=true` até o `finally` ⇒ se uma execução ficar lenta, as próximas execuções são ignoradas.
  - `readAggregatedStatus()` tenta `GET http://127.0.0.1:<PORT>/api/status` com timeout **15s** antes de cair em fallback.
  - `postPayload()` para o CT usa `DASHBOARD_TIMEOUT_MS` com default **8000ms** (AbortController).

**Implicação prática**: em um host muito carregado, é possível haver “buracos” de telemetria > 30s (e, no limite, > 130s), o que faz o CT marcar OFFLINE pelo critério atual.

### B) Dá pra “garantir 110%” que o host sempre envia e o CT sempre recebe?

No estado atual, **não existe garantia absoluta** por construção, porque:

- o envio roda no mesmo processo/event loop do `conveniente`,
- o CT persiste snapshots em disco de forma síncrona e pode responder 500 em falha de IO,
- e há dependências externas (rede/DNS, endpoint do CT).

O que dá para fazer (estratégias enterprise, para execução futura) é reduzir drasticamente a chance de falso OFFLINE:

- **Heartbeat mínimo separado do snapshot pesado**:
  - enviar um “ping leve” mais frequente (ex.: 5–10s) com `hostId + uptime + ts`;
  - manter o snapshot completo a cada 30s (ou sob demanda);
  - CT marca ONLINE pelo heartbeat e mostra “snapshot stale” separadamente.
- **Isolar telemetria do caminho crítico**:
  - mover envio para subprocesso/worker dedicado (ou pelo menos separar “snapshot” e “sender”), para não depender do Robe/Virtus.
- **SLO explícito e auditável na UI**:
  - quando OFFLINE, mostrar “CT não recebeu `/report` há Xs” (evita confundir “máquina acessível” com “telemetria chegando”).

> Nota: propostas; **não implementar agora** (somente mapear e registrar).

### C) “Pode ser 10 segundos em vez de 30?”

**Tecnicamente sim**, mas precisa de decisão consciente (trade-off) e evidência:

- **Pró**: reduz tempo até o CT perceber que o host está vivo.
- **Contra**:
  - aumenta tráfego e escrita em disco no CT (cada report gera persistência de snapshot),
  - aumenta probabilidade de overlap se a coleta do status ou a rede estiverem lentas,
  - aumenta risco de “flapping” visual se o grace/critério não estiver alinhado.

Antes de mexer em intervalo, definir:

- SLO esperado (ex.: “report a cada 10s; tolerar até 60s sem marcar OFFLINE”),
- qual dado define ONLINE (ex.: heartbeat leve) vs “dados detalhados” (snapshot),
- e o que a UI faz quando o host está ONLINE mas o snapshot detalhado está stale.

### D) O CT (`sitechatbot`) está “perfeito” para receber?

Ele está funcional e tem validação/persistência, mas não é “perfeito/garantido” ainda.

Evidências:

- `C:\sitechatbot\index.js` `POST /report` (`handleReport`)
  - calcula `hostId` (prioriza `payload.hostId`) e tenta persistir snapshot em disco (`salvarSnapshot`).
  - se falhar ao salvar, retorna HTTP 500 ⇒ host não recebe `ok:true`.
- A persistência usa IO síncrono (atômico, porém sujeito a `EPERM/EBUSY`/antivírus/disco em Windows).

### E) Como o host escolhe qual CT chamar (e onde pode dar ruim)

O endpoint de report é resolvido por `C:\conveniente\scripts\notifierEndpoints.js`:

- prioridade 1: `CT_BASE_URL`/`CT_URL` (env) ⇒ `{base}/report`
- prioridade 2: `C:\conveniente\dados\ct_config.json` (`ctBaseUrl`) ⇒ `{ctBaseUrl}/report`
- fallback: `CT_NOTIFIER_REPORT_URL` (env) ou URL ngrok hardcoded.

Se o host estiver com CT URL errada (ou ngrok expirado), ele pode “rodar normal”, mas o CT para de receber `/report` e marca OFFLINE.

### F) Proposta “ultra enterprise” alinhada com a ideia do humano (sem CT pingar host direto)

Você sugeriu:

- “host só envia quando muda” (para o dashboard ficar estável e ‘verdadeiro’)
- “CT pergunta pro host se tá online” (para confirmar)

**Essência correta.** Só tem uma restrição técnica importante no nosso sistema atual:

- o `conveniente` é **localhost-only** (bind `127.0.0.1`), então o CT normalmente **não consegue fazer HTTP direto** para o host para “perguntar se tá online”.

Então, para manter a essência e ficar enterprise, a forma robusta é:

#### Modelo recomendado: 2 canais (heartbeat leve + snapshot/delta)

1) **Heartbeat leve (sempre)**
- Host envia um payload mínimo com alta frequência (ex.: 5–10s):
  - `hostId`, `sentAt`, `uptime`, `pid`, `version/git_head` (opcional), e um `seq` monotônico.
- Isso define **ONLINE** de forma barata e confiável.

2) **Snapshot/delta (só quando muda)**
- Host mantém um “estado base” e calcula `hash` (ex.: SHA1 do JSON normalizado ou de um subconjunto).
- Só envia o snapshot completo (ou delta) quando o `hash` mudar.
- Mesmo assim, manda um “full refresh” bem menos frequente (ex.: a cada 5–15min) para autocorreção.

**Como isso elimina falso positivo**:
- O CT não confunde “máquina acessível” com “telemetria chegando”:
  - **ONLINE** = heartbeat recente
  - **DADOS ATUALIZADOS** = snapshot recente (ou delta aplicado)
- A UI pode mostrar claramente:
  - “Host ONLINE (heartbeat há 7s)”
  - “Snapshot stale (última mudança há 12min)” (não é OFFLINE)

#### “CT perguntar se tá online” (sem rede host→CT): usar o canal de comandos

Se você quiser que o CT faça uma checagem ativa, o jeito enterprise no nosso stack é:

- CT enfileira um comando (`ping`/`health_bundle`) para o `hostId`
- o host **recebe esse comando dentro da resposta do `/report`** e responde com **ACK** (evidence)

Ou seja, não é um “ping TCP”, é um “ping lógico” via o próprio mecanismo CT⇄host já existente (fila/ACK). Isso é auditável (tem `cmdId` e `ack_<cmdId>.json`).

#### Garantia de entrega (camada de confiabilidade)

Para ser “ultra robusto” (sem perder report):

- Host guarda em disco um pequeno spool do último heartbeat/snapshot pendente (ex.: `telemetry_outbox.jsonl`) e só descarta após receber `ok:true` do CT.
- CT, ao receber, salva em 2 camadas:
  - snapshot atual (`dados/<hostId>-*.json` ou idealmente `dados/<hostId>.json`)
  - journal append-only (`dados/reports.jsonl` ou SQLite) para auditoria/forense

> Isso transforma “falhou 1 request” em “atrasou, mas não perdeu”.

#### O que fica explícito como decisão (antes de executar)

- Frequência do heartbeat (5s/10s/30s)
- Frequência de refresh completo (ex.: 10min)
- Critério de OFFLINE (ex.: “sem heartbeat por 180s”)
- Critério de “stale snapshot” (ex.: “sem snapshot/delta por 15min”)
- UX do dashboard: ONLINE vs STALE vs OFFLINE (3 estados, não 2)

## Garantias “não ficar à mercê do Robe/Virtus” (isolamento do setor de telemetria)

### Problema atual (realista)

Hoje, o envio de telemetria (`/report`) roda dentro do mesmo processo do `conveniente` (`C:\conveniente\scripts\dashboard.js`), com `inFlight` e dependência do event loop. Isso significa:

- se o event loop ficar lento/bloqueado por carga, **o heartbeat/snapshot atrasam**
- como existe anti-overlap (`if (inFlight) return`), um tick lento pode causar **pulos** de telemetria

### Requisito enterprise

Telemetria precisa ser um “setor próprio”: **não pode depender do caminho crítico** de Robe/Virtus.

### Estratégias compatíveis (para execução futura; aqui só registro)

1) **Sender isolado em subprocesso**
- o processo principal só escreve “o que deve ser enviado” num spool local (arquivo pequeno)
- um subprocesso dedicado faz:
  - retry com backoff
  - confirmação de entrega (recebeu `ok:true` do CT)
  - sem concorrer com Robe/Virtus

2) **Heartbeat mínimo + snapshot/delta separado**
- heartbeat é barato e pode ser mais frequente mesmo em carga
- snapshot pesado é best-effort e pode atrasar sem virar OFFLINE

3) **Outbox persistente (não perder dados)**
- host grava um outbox (ex.: `telemetry_outbox.jsonl`) e só remove quando confirmado
- isso evita “perdi telemetria porque 1 POST falhou”

### 3) Lista de riscos que não podem ficar de fora (P0/P1)
