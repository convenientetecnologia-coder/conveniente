## Hipótese principal (a provar e corrigir)

O sistema está deixando perfis “permanentemente fechados” porque algum fluxo **desliga `desired.active=false`** quando a abertura fica parcial.

Evidência por código (sem mudar ainda):

- `C:\conveniente\scripts\worker.js` contém um bloco `open_all_finalize_partial` que, quando detecta que todos os pendentes foram negados por RAM/supervisor, **desliga `desired.active=false`** para esses perfis (evita loop infinito, mas viola a regra do negócio “sempre aberto”).

## Gates e bloqueadores que podem manter browser fechado (inventário completo)

Mesmo com `desired.active=true`, um perfil pode ficar temporariamente fechado por:

- **Shard**: perfil fora do shard do worker (`SHARD_SET` / `inShard(nome)`).
- **Backoff**:
  - `robeMeta[nome].activationHeldUntil > now`
  - `robeMeta[nome].reopenAt > now`
- **Supervisor slots/ram**:
  - `supervisorClient.requestOpen(...)` pode negar (`slots`, `ram_low`, etc).
- **RAM gate**:
  - `getOpenMinFreeMB(operator)` e `freeMB <= minFreeMB` em `activateOnce` ⇒ `ram_insuficiente_para_ativar`.
- **Provision lock**:
  - `activation_hold_by_provision_lock` quando outro operador detém o lock de provision.

**Importante**: nenhum desses deveria virar “fechado permanente”; apenas pendência/backoff.

## Mapa de código (callers/callees) — onde “fechar vs abrir” é decidido

### Writer de intenção (desired)
- `fileStore.withDesiredFileLockUpdate(...)` escreve `C:\conveniente\dados\desired.json`.

### Quem abre browser (executor)
- `activateOnce(nome, source)`:\n
  - gate RAM: `getOpenMinFreeMB(operator)` (considera provision lock)\n
  - supervisor gate: `supervisorClient.requestOpen(...)` (pode negar slots/ram)\n
  - abre Chrome e cria `controllers.set(nome, ...)`

### Quem decide “tentar abrir os faltantes” (loop)
- `nurse()` percorre `desired.perfis` e tenta abrir perfis com `want.active=true` e `!controllers.has(nome)`, respeitando `activationHeldUntil/reopenAt`.

### Onde pode virar “fechado permanente” (suspeito P0)
- `open_all_finalize_partial`:\n
  - hoje faz `d.perfis[nn] = { ...cur, active:false }` para pendentes negados por RAM/supervisor.\n
  - isso explica `perfisTotal > activeBrowsers` mesmo com RAM suficiente depois.

### Patch P0 (RM1): abrir mesmo em captcha/identidade quando `ctrl` está ausente

**Causa raiz observada em runtime (RM1)**:

- Perfis com `loginRequired` (captcha/checkpoint) ou `identityRequired` ficavam **fechados** porque o `nurseTick` dava `continue` nesses estados mesmo sem `ctrl` (sem browser aberto), impedindo a abertura.

**Correção**:

- Se `flags.loginRequired` indicar captcha/checkpoint e `ctrl` estiver ausente, não bloquear a abertura: deixar cair no bloco `want.active===true && !ctrl` para abrir e só então rodar `runCaptchaFlow`.
