============================================================
OBJETIVO EXECUTADO
============================================================
Conectar o Ouvido (worker.js) as Maos (virtusDelta.js) para:
1) Nunca perder mensagem do cliente.
2) Diferenciar Chat Novo vs Chat Ativo.
3) Chat Novo: buffer 60-120s com acumulacao.
4) Estouro do timer: Maos abrem chat, raspam cidade, enviam saudacao humana.
5) So depois da saudacao: despacho unificado ao CT.
6) Chat Ativo: envio imediato em tempo real.

============================================================
O QUE FOI IMPLEMENTADO - WORKER (OUVIDO)
============================================================
1) Estado por thread_key com persistencia local:
- Novo arquivo de controle local: dados/delta_thread_state.json
- Estrutura em memoria por thread:
  - status: new_buffering | hands_in_progress | active
  - mensagens acumuladas
  - seq da mensagem
  - cidade conhecida
  - timer atual e falhas de hands
- Persistencia debounced para robustez operacional.

2) Bifurcacao de estado no onFrame:
- Fluxo agora decide por thread:
  - Chat Ativo: despacho imediato para CT.
  - Chat Novo: nao despacha na hora, arma timer 60-120s e continua acumulando.

3) Buffer de acumulacao 1-2 minutos:
- Timer inicial randomico de 60-120s.
- Mensagens subsequentes durante timer seguem entrando no buffer.
- Continua acumulando inclusive quando o status esta hands_in_progress.

4) Garantia de registro total de mensagens:
- Toda mensagem validada e gravada em mensagens_pendentes.jsonl como captura forense:
  - dispatch_ct=false
  - queue_mode=capture_only
  - event=lead_capturado_buffer
- Isso garante trilha integral de tudo que o cliente digitou.

5) Acionamento automatico das Maos ao estourar timer:
- Worker chama o runner Delta e dispara:
  - enqueueDeltaGreetingFlow(thread_key, mensagens_cliente)
- Se falhar, agenda retry automatico (20-35s), sem perder buffer.

6) Despacho unificado para o CT apos sucesso das Maos:
- So apos saudacao enviada com sucesso no Facebook:
  - gera payload consolidado com mensagens concatenadas + cidade
  - dispatch_ct=true
  - event=lead_consolidado_pos_hands
  - kick do ingest loop para envio ao /api/messenger-delta/ingest

7) Chat ativo em tempo real:
- Depois do ciclo de chat novo concluido, thread vira active.
- Mensagens novas passam a sair imediatamente para CT:
  - event=lead_chat_ativo_realtime
  - dispatch_ct=true

8) Ajuste no ingest:
- Linhas forenses (dispatch_ct=false) agora:
  - avancam cursor
  - NAO fazem POST ao CT
- Linhas de despacho (dispatch_ct=true) continuam enviando ao CT.

9) Hardening de deduplicacao:
- Saiu dedupe global permanente por texto.
- Entrou dedupe curto por janela (3.5s) por thread para bloquear fantasmas sem matar mensagens legitimas repetidas em tempos distintos.

============================================================
O QUE FOI IMPLEMENTADO - VIRTUSDELTA (MAOS)
============================================================
1) Nova rotina de saudacao de chat novo:
- Funcao nova: sendDeltaGreetingNow({ threadKey, mensagensCliente })
- Fluxo dessa rotina:
  - aplica cooldown global anti-robotico
  - tenta extrair cidade do DOM (antes)
  - monta saudacao via generateDeltaGreeting(atendimentodelta.json)
  - executa sendReplyFlow(..., fromNetworkLead: true)
    - inclui abertura do thread (openThreadByClick)
    - digitacao humanizada (typeHumanized)
    - quebra composta com Shift+Enter
  - tenta extrair cidade novamente (depois)
  - retorna cidade, origem da cidade, profile_url e texto da saudacao

2) Nova API do runner exposta para o worker:
- enqueueDeltaGreetingFlow({ thread_key, mensagens_cliente })
- Mantida serializacao pela fila interna (createSerialQueue) para evitar concorrencia de UI.

BLOCO A - ENTRADA DE MENSAGENS (OUVIDO/CDP)
------------------------------------------------------------
Cenario A1 - Frame invalido/corrompido
Entrada:
- CDP entrega frame malformado.
O que o sistema faz:
- Tenta decode/extract.
- Se falhar, captura excecao e nao derruba o worker.
Resultado:
- Sem crash global.
Acao operador:
- Nenhuma imediata; monitorar logs DELTA_CDP_ERROR apenas se recorrente.

Cenario A2 - Mensagem filtro negativo (vazia, mid., token 32/38, ruido numerico longo)
Entrada:
- Texto nao elegivel por __deltaShouldEmitLeadText.
O que o sistema faz:
- Ignora a mensagem para fluxo de negocio.
Resultado:
- Nao entra em buffer e nao vai para CT.
Acao operador:
- Nenhuma; comportamento esperado de higiene de ingestao.

Cenario A3 - Mensagem valida entra no ouvido
Entrada:
- thread_key valido e texto valido.
O que o sistema faz:
- Cria/recupera estado da thread.
- Aplica dedupe curto (janela 3.5s) anti-fantasma.
- Sempre grava trilha forense capture_only no JSONL.
Resultado:
- Nenhuma mensagem valida fica sem rastreio no arquivo.
Acao operador:
- Se auditar, conferir event=lead_capturado_buffer.

Cenario A4 - Mensagem repetida em <= 3.5s (fantasma tecnico)
Entrada:
- Mesmo texto/op em janela curtissima.
O que o sistema faz:
- Bloqueia por dedupe curto.
Resultado:
- Evita duplicacao artificial.
Acao operador:
- Nenhuma, a nao ser que ambiente gere spam real.

Cenario A5 - Mensagem repetida apos janela > 3.5s
Entrada:
- Cliente realmente repete texto depois.
O que o sistema faz:
- Considera legitimo e processa normalmente.
Resultado:
- Nao perde repeticoes humanas reais.
Acao operador:
- Nenhuma.

BLOCO B - CHAT NOVO (BUFFER 60-120S)
------------------------------------------------------------
Cenario B1 - Primeira mensagem de thread desconhecida
Entrada:
- Estado inexistente para (nome, thread_key).
O que o sistema faz:
- Cria estado new_buffering.
- Arma timer randomico 60-120s.
- Continua coletando.
Resultado:
- Nao despacha para CT ainda.
Acao operador:
- Nenhuma; esperar timer.

Cenario B2 - Varias mensagens durante timer
Entrada:
- Cliente manda novos baloes antes do estouro.
O que o sistema faz:
- Cada mensagem entra no buffer da thread.
- Todas ficam registradas no JSONL forense.
Resultado:
- Texto consolidado cresce progressivamente.
Acao operador:
- Nenhuma.

Cenario B3 - Timer estoura com maos disponiveis
Entrada:
- Timer de chat novo chega ao fim.
O que o sistema faz:
- Move estado para hands_in_progress.
- Chama enqueueDeltaGreetingFlow no runner Delta.
Resultado:
- Inicia fase visual (abrir chat, coletar cidade, digitar saudacao).
Acao operador:
- Nao interromper navegador da conta.

Cenario B4 - Mensagem chega enquanto hands_in_progress
Entrada:
- Cliente manda mensagem no exato momento do trabalho das maos.
O que o sistema faz:
- Continua acumulando no buffer normalmente.
- Continua registrando capture_only.
Resultado:
- Sem perda de texto durante automacao visual.
Acao operador:
- Nenhuma.

Cenario B5 - Maos concluem com sucesso
Entrada:
- sendDeltaGreetingNow retorna ok=true.
O que o sistema faz:
- Concatena mensagens acumuladas.
- Enfileira lead_consolidado_pos_hands (dispatch_ct=true).
- Marca status da thread como active.
- Limpa historico interno consolidado daquela thread.
Resultado:
- CT recebe pacote unificado para criar/abrir card.
Acao operador:
- Validar no CT o surgimento do card novo.

Cenario B6 - Maos falham (openThread/cidade/digitacao/envio)
Entrada:
- enqueueDeltaGreetingFlow retorna erro.
O que o sistema faz:
- Volta estado para new_buffering.
- Agenda retry automatico (20-35s).
- Registra lead_hands_retry_scheduled (capture_only).
Resultado:
- Fluxo nao morre; entra em reprocesso.
Acao operador:
- Se repetitivo, checar UI do Facebook e estabilidade da sessao.

Cenario B7 - Retry posterior das maos funciona
Entrada:
- Nova tentativa timer retry.
O que o sistema faz:
- Repete fase hands.
- Em sucesso, despacha consolidado e ativa thread.
Resultado:
- Recuperacao automatica sem perda.
Acao operador:
- Nenhuma apos normalizacao.

Cenario B8 - Retry falha varias vezes
Entrada:
- Ambiente hostil (DOM quebrado, browser instavel, virtus indisponivel).
O que o sistema faz:
- Mantem ciclo de retries e acumulacao.
Resultado:
- Mensagens continuam registradas; card pode atrasar.
Acao operador:
- Intervencao operacional: recuperar sessao/virtus para destravar hands.
