## Hipóteses (a provar) — mesma árvore do RM2

**H0) “Fallback para []” ao ler `perfis.json` durante `stock_provision` (gera wipe para 1 perfil)**:

- `stock_provision` cria perfil via `POST /api/perfis` (no host),
- `POST /api/perfis` usa `fileStore.withPerfisFileLockUpdate()`,
- `withPerfisFileLockUpdate()` lê `perfis.json` via `readJsonSafe(perfisPath, [])`,
- `readJsonSafe()` devolve `[]` se o JSON está inválido ou o arquivo está ausente,
- o mutator adiciona somente o perfil novo e grava — resultando em `perfisCount=1`.

Isso casa com a evidência do CT (36→1) e com a correlação temporal do comando `stock_provision` (`cmdId=e359f560-...`).

**Nota: “Fechar todos” (close-all) não grava `perfis.json` (mas grava `desired.json`)**:

- `POST /api/perfis/close-all` lê `perfis.json` para listar targets, grava `desired.json` (via `withDesiredFileLockUpdate`) e manda o worker desativar.
- Portanto, `Ctrl+C` durante close-all é suspeita válida de crash/IO, mas o write direto do close-all é em **`desired.json`**, não em `perfis.json`.

**H1) IO: janela unlink→rename + crash** (arquivo fica ausente) — ver `C:\conveniente\scripts\fileStore.js` (`writeJsonAtomic`).

**H2) bootstrap recriou vazio** (ex.: `ensurePerfisJson()`) e o sistema começou do zero — ver `C:\conveniente\scripts\fileStore.js`.

**H3) write parcial por shard** (subconjunto) — ver `C:\conveniente\scripts\worker.js` (shard filter + bloqueio de write em shard, evento `perfis_write_blocked_worker_shard`).

**H4) comando destrutivo** (cleanup/migrate/delete) — provar via CT (`commands.log` + `ack_*.json`).
