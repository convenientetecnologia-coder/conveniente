## Objetivo

Garantir que o sistema opere como **um único corpo** com **uma única fonte da verdade** para:

- **motoristas por cidade/grupo** (incluindo `active` + `test`)
- **engajamento/chamados por cidade/grupo** (origem: pedidos WhatsApp → grupos)

## Definições canônicas (contrato do “único ser vivo”)

### Conceitos (o que significa cada número)

- **Motoristas**: contagem de cadastros em `ct_drivers` com `status IN ('active','test')` por `city_uf`.
  - Regra: **`test` conta** (consome engajamento e precisa entrar na capacidade).
- **Chamados / Engajamento**: contagem de pedidos com `status='sent'` por `cidade_uf` agregada por grupo (matriz + secundárias).
  - Regra: “chamados” = **saída real** do pipeline WhatsApp→Pedidos→Notificador→Grupo (não é estimativa).
- **Contas por grupo**:
  - **A (ativa)**: perfil sem `loginRequired`, sem `banned`, e não classificado como `limit_exceeded`.
  - **LR (login requerido)**: perfil com `loginRequired=true` (motivo define subclasse: captcha/login/session/identity/2fa/…).
  - **LE (limite excedido)**: perfil classificado como `limit_exceeded` (derivado do Robe/robeRec quando disponível).
  - **B (banida)**: perfil com `banned=true` (sempre vence).

### Precedência (MUTUAMENTE EXCLUSIVO)

Regra: **um perfil não pode cair em 2 estados ao mesmo tempo**.

Precedência canônica (mais grave/acionável primeiro):

`B > captcha > two_factor > identity > consent > login/session/login_other > LE > OK`

Evidência: `C:\sitechatbot\convenientetecnologia\lib\fbAccountState.js` (comentário e função `classify`).

### Modos de “supply” (contas): inventário vs operacional

Regra: existem 2 visões permitidas, mas **nunca misturadas sem declarar explicitamente**:

- **operacional (online-only)**: decisões automáticas (scheduler/provision/alertas). Evita distorção por host stale.
- **inventário (includeOffline)**: UI pode usar para “não piscar”, mas deve mostrar badge `includeOffline=1` e não pode ser usada para tomada automática de decisão.

### Janelas (demand) — sempre explícitas

Regra: nenhuma tela pode mostrar “Chamados (janela)” sem dizer **qual janela**.

- `recent3d_start_of_day`: últimos 3 dias (start-of-day) até agora.
- `h24_rolling`: últimos 24h rolling.
- `h72_rolling`: últimos 72h rolling.

## Evidência (prova em código) — hoje existem múltiplas “verdades”

### 1) Virtus → Grupos usa janela **recent3d** e classificador simples (fonte potencialmente falha)

Arquivo: `C:\sitechatbot\index.js` endpoint `GET /api/dashboard/virtus`.

- **Engajamento/chamados**: `pedidosStore.getCountsByCity(... sent_at ...)` em janela **recent3d** (3 dias, start-of-day).
- **Motoristas**: `ctStore.getDriverCountsByCityUF({ statuses: ['active','test'] })`.
- **Contas A/LR/LE/B**:
  - `LE` só é contado quando `p.estado === 'paused_limit'` (pode não refletir o estado real do Robe/robeRec).
  - não usa `fbAccountState.classify`.

Risco: LE e outros estados podem ficar **invisíveis** se o snapshot não preencher `p.estado` corretamente.

### 2) Contas Facebook v2 usa `computeAccountsByGroupFromSnapshots` + `fbAccountState.classify` (fonte mais próxima da verdade operacional)

Arquivo: `C:\sitechatbot\index.js` endpoint `GET /api/contas-facebook-v2`.

- Contas por grupo vêm de `computeAccountsByGroupFromSnapshots(...)`, que usa:
  - `fbAccountState.classify({ perfil, robeRec })`
  - breakdown por servidor
  - categoria por `robeMode/entity_kind` (com travas)

Isso enxerga estados que a tela Virtus→Grupos pode não enxergar (ex.: LE via robeRec/robeEstado).

### 3) Janelas diferentes (recent3d vs 72h rolling) geram números diferentes “com razão”, mas a UI não deixa isso explícito

Exemplo: recent3d começa no início do dia; 72h rolling é janela contínua.

Se a tela não exibir “qual janela”, o humano compara errado.

## Diagnóstico (RCA)

O CT hoje tem **fontes divergentes** para o mesmo “conceito”:

- **Demand**: mesma tabela (pedidos), mas janelas diferentes e às vezes sem clareza.
- **Supply** (contas): classificador simples (`p.estado`) vs classificador canônico (`fbAccountState`).
- **IncludeOffline**: algumas telas contam ONLINE+OFFLINE para “não piscar”; outras usam ONLINE para “realidade operacional”.

Isso cria decisões inconsistentes (UI mostra A mas algoritmo enxerga LE/LR ou vice-versa).

## Decisão: fonte única e regras explícitas

### Fonte Única (canônica)

1) **Motoristas**: `ctStore.getDriverCountsByCityUF({ statuses: ['active','test'] })`
2) **Engajamento**: `pedidosStore.getCountsByCity(...)` com janelas explícitas (ver abaixo)
3) **Contas por grupo**: `computeAccountsByGroupFromSnapshots(...)` (usa `fbAccountState.classify`)

### Janelas (contrato)

Para cada tela/algoritmo, a janela deve estar no payload e na UI:

- `recent3d` (3 dias, start-of-day) — bom para “visão humana”
- `h72_rolling` (72h rolling) — bom para cálculo operacional (score/idealA)
- `h24_rolling` (24h rolling) — bom para “agora”

### Online vs Offline (contrato)

Precisamos de duas leituras válidas, ambas explícitas:

- **operacional (online-only)**: usada para decisões automáticas (provision/scheduler) e alertas P0.
- **inventário (includeOffline)**: usada apenas para UI “não piscar”, mas nunca para decisão automática sem deixar claro.
